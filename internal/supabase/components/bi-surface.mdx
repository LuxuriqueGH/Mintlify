**Read latency — why these functions were slow, and what is still slow (2026-08-19).** The cost driver is **not** query logic, it is how many `activity_log` rows have their wide `record` jsonb read. 30,925 rows carry `object='opportunity'`; 14,812 of them exceed the inline threshold and live in the 98 MB TOAST table. Measured on that slice: counting rows without touching `record` takes **647 ms**, touching one key **6,615 ms**, touching seven keys **7,754 ms** — so the cost is the TOAST fetch per row, essentially flat in the number of keys extracted. Any function that reads `record` per event pays ~6 s and no index changes that.

- **Fixed by reading fewer rows.** `opportunity_current` selected its winner with a `row_number()` window over all 30,925 events; it now uses a **loose index scan** (recursive skip-scan over `activity_log_object_record_idx`, 609 index descents, 11 ms) plus one `LATERAL … LIMIT 1` per deal, so `record` is read for ~609 rows. Repeated warm evaluation went from **43 ms best / 1,407 ms mean / 5,491 ms worst** to a stable **19 / 23 / 32 ms** — the stability matters as much as the mean, since the old shape depended on ~83 MB of TOAST staying resident in a **224 MB** `shared_buffers`. This lifts all six dependants: `opportunity_cashflow` 1,124 → **331 ms** (it alone runs **22× per dashboard visit**), `data_quality` 949 → **399 ms**, `pipeline_by_start` 617 → **334 ms**, `opportunity_rollup` 262 → **107 ms**. `opportunity_daily` separately skips events superseded within the same Tokyo day (23,777 of 30,925 are zero-width and can match no spine day — see that migration's proof), measured **2.4× warm / 3× cold** in an interleaved A/B.
- **Still slow, and not fixable in SQL.** `opportunity_inflow`, `opportunity_stage_flow`, `opportunity_stage_winrate`, and therefore `opportunity_demand_projection` and `opportunity_forecast_with_projection` (10–17 s, high variance) all need **every event's `stage`**, so they pay the full TOAST scan by construction. `inflow`'s `reached_qualified` counts any dwell (ADR-0025), so intra-day events are load-bearing there and the `daily` trick is invalid. A distinct-pairs rewrite of `inflow` was tried and **reverted as a 25–40% regression** (`stage_dim` is 14 cached rows, so its 12.4M probes cost almost nothing — probe count was never the bottleneck). The only remaining lever is denormalising `stage` out of the jsonb into a typed column: the equivalent per-event stage walk off a narrow column measures **58 ms vs 12,716 ms**. That is a table rewrite. Sasha ruled "Do it, next session" on 2026-09-25; `supabase-044` in `BACKLOG.md` holds the task and the times of 2026-09-25.
- **Amplifiers outside this schema.** A full dashboard visit fires 35 statements with `cache_timeout` null at chart, dataset and database level, and `refresh_frequency: 1800` re-runs the active tab every 30 minutes with no tile exempt. Since the functions take no arguments and Preset wraps virtual-dataset SQL as a subquery, the Date Range filter is an **outer** `WHERE` — full history is computed, then discarded. Production worst case was **117,473 ms against `preset_ro`'s 120 s `statement_timeout`**. These are `../Superset` decisions, not schema ones.

**Fiscal-year dimension — retired (ADR-0033, 2026-07-29):** every date-bearing function used to emit `period` (absolute label, e.g. `FY26-27`) + `fy_offset` (relative int) derived from two shared helpers, `analytics.fy_label(date)`/`fy_offset(date)` (ADR-0018), scoped by a single dashboard "Fiscal Year" native filter. **All of it is gone:** the helpers are dropped, `period`/`fy_offset` are dropped from all 7 functions that emitted them, and the Fiscal Year filter is deleted. **All time scoping is now the dashboard's single Date Range filter**, applied directly to each surface's day/month columns (`inquiry_date`/`created_date`, `snapshot_date`, `transition_date`, `day`/`project_day`, `start_day`, `forecast_month`). The one place a May→April window survives is a **presentation-tier default** on that Date Range filter (D10) — a user-overridable GUI convenience, not a schema, dataset, metric, or chart or filter target; nothing downstream of the filter control knows a fiscal year exists. See [ADR-0033](../adr/0033-retire-fiscal-year-dimension.md). **Decision:** [ADR-0011](../adr/0011-bi-surface-via-analytics-schema.md) + [ADR-0012](../adr/0012-analytics-surface-definer-functions-not-views.md) (definer functions, not views) + [ADR-0024](../adr/0024-bi-semantic-contract.md) (semantic contract: meaning in the DB, metrics as code in `../Superset/scripts/setup_preset.py`, charts display only) + [ADR-0033](../adr/0033-retire-fiscal-year-dimension.md) (fiscal-year dimension retired; Date Range filter is the sole time-scoping mechanism) **Consumer repo:** [`../../../Superset`](../../../Superset) (Preset.io — the sole BI tool)

## What it is

The read surface for **Superset (Preset.io)** — kept deliberately separate from the `public` service-role surface. A private **`analytics` schema** of **aggregate-only, SECURITY DEFINER functions** (`analytics.<name>()`), read by a dedicated least-privilege login role, **`preset_ro`**.

## Responsibilities

- Expose business metrics at **group grain only** — no per-deal names or amounts.
- Let a BI tool connect with the **smallest possible blast radius**: a leaked credential exposes aggregate numbers, never raw CRM rows.

**Conservation** (ADR-0021 as extended by ADR-0024, as ADR-0049 restates it). Every rider term is a data-quality fact that `analytics.data_quality()` reports; none is silently absorbed. The form below is live since the ADR-0049 apply of 2026-09-18 (every delta 0 at apply).

2. `SUM(projected, won buckets)` = the won total + `cash_over_nominal`. Won Value then carries over-receipts, as ds44 always did.
3. unchanged.
4. `SUM(pipeline_by_start.gross)` + `no_start_date` = the invariant-1 total.
5. unchanged.

7. `no_payment_date` = ds43 `undated_gross`, to the yen.

> **Date-quality caveat (ADR-0021 scope note):** projected buckets on `month(coalesce(dateProjectedN, startDate))`, so an installment with an amount but no projected date is `dated` via the deal's **start date** (a proxy), not `undated`. "Won value with no payment date" via `month IS NULL` therefore counts only the _no-date-at-all_ (`undated`) bucket, not the start-date-proxied portion (Sasha's call, 2026-06-29). **Once ADR-0049 applies this caveat covers unwon deals only** — a won deal is dated by its receipts and by FIFO on the unpaid schedule, so no `startDate` proxy applies to it and its undated money is exactly `data_quality()`'s `undated_outstanding` plus its undated receipts.

**Win-rate readings (`opportunity_stage_winrate`):** the function returns component counts, not a rate, because a ratio isn't additive under re-slicing. Compute in Superset as `SUM(completed)/SUM(reached)` (raw — counts in-flight deals as not-yet-won, biased low while data is young) or `SUM(completed)/NULLIF(SUM(completed)+SUM(lost),0)` (resolved — win-rate among _finished_ deals). `still_open` is the not-yet-resolved mass that separates the two. "Reached stage X" is cumulative (highest ladder rung _genuinely_ attained ≥ X), so stage skips don't undercount and `reached` is monotonic down the ladder. **Genuinely reached = total time-in-stage ≥ 1 hour, or it's the deal's current stage** — a stage the deal merely flickered through (e.g. mis-set to QUALIFIED for a minute, then corrected) does _not_ count, so stage-correction churn can't inflate a deeper stage's denominator. The current stage is always exempt from the 1h gate (the present state is never a correction artifact). Time-in-stage is reconstructed from `activity_log` event gaps (`lead()`), threshold is a literal `interval '1 hour'` in the function. Since ADR-0051 (2026-09-25) the event gaps and stages come from the view `public.opportunity_stage_spans`, where an `analytics.stage_history_override` interval replaces the logged stage (the 2026-08-13 workflow-test POST_EVENT edits are the first rows). **Every live deal counts as reaching NEW** (rung floored at 1): a deal captured straight into a terminal/off-ladder stage (REJECTED / LOST / ON_HOLD — common for pre-capture deaths that collapse onto a first already-terminal snapshot) still lands at NEW with its disposition, so intake losses aren't hidden. Completion is keyed on a rung the deal must genuinely have reached, so the floor never invents a win.

**The won line is `stage_dim.is_won` = CONTRACTED+ (ADR-0048, 2026-09-16).** `completed` means _ever reached the won line_ — CONTRACTED (rung 7) or later — the same line `opportunity_rollup` / `inflow` / `daily` / `cashflow` / the forecast use. Sasha's rule: a deal is won from CONTRACTED onward, unless it is now LOST, REJECTED or ON_HOLD. **Column names have never changed** through three moves of this line (`completed`, `completed_value`, …) — they are dataset 42's stable API — so the ds42 metrics change meaning, not name.

**ADR-0048 is applied (2026-09-16).** The migration `20260916130000_won_line_contracted.sql` ran on Sasha's go; the live line is CONTRACTED+. After apply: `completed` 160 at CONTRACTED, `still_open` 0 from CONTRACTED up.

Its history: until 2026-07-31 this one surface required COMPLETE (rung 11, delivery finished), a narrower "win" than every neighbouring KPI; ADR-0034 repointed it to CONTRACTED (rung 7) and made `stage_dim.is_won` the single lever. ADR-0038 then moved the line itself to PRE_EVENT on 2026-08-20, because Twenty repriced the CONTRACTED stage to **0.95** probability — a signed contract is a 95% expectation, not a certainty. ADR-0048 moves it back to CONTRACTED on Sasha's ruling that everything from CONTRACTED onward is won unless proven otherwise. Twenty still prices that stage at 0.95; ADR-0050 (2026-09-18) makes that moot — no weighted metric reads Twenty's probability since 2026-09-18, and a won deal weighs 100%; the nominal won metrics carry no probability and do not move. Neither move needed a function edit: one `stage_dim` UPDATE, and `bucket`, this rung, `inflow.is_won` and `rollup` all follow. `still_open` reads 1 at CONTRACTED and 0 at rungs 8–11 today, and 0 from rung 7 up once ADR-0048 applies.

**Reader-facing, the won band is "Won"** (ADR-0048) — "Contracted" names the stage only, and the band word ADR-0038 introduced is banned from every label. **"Pipeline" means live unwon deals only**: `bucket = 'open'`, which after this migration is exactly NEW, PRE_QUALIFICATION, QUALIFICATION, FRAMEWORK, QUALIFIED and COMMITTED. The whole non-lost aggregate is **Total Value**. Every label lives in `../Superset/scripts/setup_preset.py` (verbose names + descriptions). Raw identifiers — `is_won`, `bucket = 'contracted'`, `won_book`, `won_gross`, `won_actual`, `completed_total` — are stable API and did **not** move.

**Won unless proven otherwise (the same-day amendment).** A deal that reached the won line and is **now** in LOST or ON_HOLD counts as `lost` / `parked`, not `completed`, at every rung it reached — its current stage outranks what it once reached. So `completed` equals `reached` at rungs 7–10 only while nothing signed is currently lost or parked, which is true of today's data but is not guaranteed; the win rate can dip below 100% deep in the funnel, and post-signature losses are visible rather than absorbed. On exactly those two states this surface and `opportunity_cashflow()`'s `bucket` now agree. They still part in one case: a deal that signed and then went **back to an open, non-terminal stage** — `bucket` calls it open, `completed` still calls it won, because the funnel question is about history ("of the deals that got this deep, how many ever crossed the won line"). That divergence is intended, not a defect; the population is empty today.

**LOST vs REJECTED:** `LOST` = a deal we wanted but didn't get (a real loss, in `lost`); `REJECTED` = inbound we _declined_ (we didn't want it) and must **not** count against the win-rate. REJECTED keeps `stage_dim.is_lost = true` for the broad terminal-lost zone the other surfaces use, but carries a finer `stage_dim.is_rejected = true` that the win-rate reads to pull it into a separate `rejected` sidecar — excluded from `reached` and from **both** denominators (`lost` = is_lost AND NOT is_rejected; raw = completed/reached; resolved = completed/(completed+lost)). So `reached(NEW)` = live-deal count **minus** the declined/rejected ones.

**Value-weighted win rate (ADR-0026):** each count column has a nominal-amount (¥) twin — `reached_value` / `completed_value` / `lost_value` / … — summing each deal's current `amount` into every rung it reached under the same filters. `win_rate_value_raw` = `SUM(completed_value)/SUM(reached_value)` and `win_rate_value_resolved` = `SUM(completed_value)/(SUM(completed_value)+SUM(lost_value))` answer "what share of the **value** in play did we win" (at NEW: of all value entering the funnel). Basis is nominal amount, not amount×probability — it's a win _rate_, not an expected-value figure. Deals with no `amount` contribute 0 (the `no_amount` data-quality check quantifies that); `reached_value` includes lost deals' value and is a ratio denominator, **not** a book total — never reconcile it against the forecast book.

The row-level view `opportunity_current` (it carries names + amounts) is **behind the privacy wall** (`security_invoker`, service-role only) and never exposed in `analytics`.

## How the isolation works (the load-bearing bit)

- The `public` analytics views are `security_invoker = on` (ADR-0010), so a normal role gets **nothing** from them — RLS on `activity_log`/`stage_dim` is deny-all.
- The `analytics` surface is **SECURITY DEFINER functions** (ADR-0012). A definer _function_ switches `current_user` to its owner (`postgres`, who bypasses RLS) for its whole body, so reading the invoker `public.opportunity_*` views inside it resolves the base-table checks as `postgres` and emits only aggregates. So `preset_ro` needs **no grant on the base tables** — only `USAGE` on `analytics` + `EXECUTE` on these functions, and it cannot reach `public` at all.
- **Why functions, not definer views (ADR-0012):** a definer _view_ does not change `current_user`, so a view wrapping the `security_invoker = on` public views fails ("permission denied"). Functions are the fix.
- `preset_ro`: `LOGIN NOINHERIT NOSUPERUSER NOBYPASSRLS`, with role-level `statement_timeout`/`idle_in_transaction_session_timeout` guards. **No password in git** — set out-of-band; until then it fails closed. **CONNECTION LIMIT 20** since 2026-09-25 (`20260925110000_preset_ro_hardening.sql`, ADR-0011 addendum): the Supavisor Pool Size is 15, and the limit must be at least that. Raise the limit if the Pool Size goes above 15.

## Gotchas

- **Never add `analytics` to `config.toml`'s exposed schemas.** It's invisible to PostgREST by default; exposing it would turn these definer functions into an API read-through hole around RLS.
- **Don't "fix" the definer functions to non-definer.** The Supabase advisor may flag SECURITY DEFINER routines — a false positive here (non-exposed schema, aggregate output, narrow grant). Dropping DEFINER reintroduces the permission-denied bug ADR-0012 fixed.
- **Never add row-level columns** (opportunity_id, name, amount) to this schema without a new ADR — it widens the leaked-credential blast radius.
- **Twenty field renames are bridged with `coalesce`, never a blind repoint.** `activity_log` is immutable (ADR-0019), so old rows keep the old jsonb key and new rows carry the new one. When Twenty renames a field, extractions become `coalesce(record->'newKey', record->'oldKey')` so both eras resolve and history doesn't zero out (e.g. `amountPaid` → `amountActualTotal`, ADR-0022). Keep the output column name stable so downstream functions/datasets don't churn.
- **Freshness:** the current functions read `activity_log` / `opportunity_current` **live** (no matview), so they reflect captured webhooks immediately. `opportunity_daily` reconstructs stage-as-of-date from the log, so only history captured since capture went live (first opp event 2026-06-17) is visible; pre-capture state collapses onto a deal's first captured snapshot.
